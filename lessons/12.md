# 12 · 幂等与状态机：让重复请求得到一致结果

第 10 周 · 首次讲解与小练习约 90 分钟，项目实践另计。

网络重试不可避免。目标不是幻想每个请求只会到达一次，而是确保同一个业务意图的重复到达不会制造多份结果。

## 幂等键的范围

将主体范围与 requestId 建联合唯一约束，保存请求指纹、taskId、状态和结果引用。相同键相同请求返回原任务；相同键不同请求拒绝冲突。记录不能在业务副作用完成之前过早删除。先查再写依然有竞争，使用数据库约束裁决，并在唯一冲突后读取已有任务。

## 状态转换也会竞争

定义 PENDING→RUNNING→SUCCEEDED/FAILED；取消可以先进入 CANCEL_REQUESTED，等工作者确认才转 CANCELLED。状态更新需带旧状态条件，防止迟到结果把已结束任务覆盖。若业务选择“成功优先”，也要明确与取消之间的裁决规则。重启后 RUNNING 任务不能永远悬挂，可设计租约、心跳与超时接管。

## 持久化任务与真实副作用

把任务记录与待发送事件放同一数据库事务可以避免“写成功但消息没发”的窗口，工作者通过 outbox 派发并重试。仍要让接收端按相同业务键去重；outbox 本身不等于全链路恰好一次。涉及外部工具时还需要接收端支持幂等或人工核对未知结果。

## 联系你的 Python 经验

这些原理与 LangGraph 状态恢复有关，但框架保存 checkpoint 并不会自动让外部建单操作幂等。恢复执行与副作用去重必须一起设计。

## 代码拆解

```sql
CREATE TABLE ai_task (
  id BIGINT PRIMARY KEY,
  owner_id BIGINT NOT NULL,
  request_id VARCHAR(100) NOT NULL,
  payload_hash VARCHAR(64) NOT NULL,
  status VARCHAR(30) NOT NULL,
  UNIQUE (owner_id, request_id)
);

UPDATE ai_task SET status = 'RUNNING'
WHERE id = ? AND status = 'PENDING';
```

影响行数为 1 才获得本次启动资格；0 行可能已被其他工作者启动。这里只演示状态竞争，完整实现还需要任务内容、结果、租约与时间字段。

## 动手任务

同一 requestId 连续提交两次，再并发提交两次，均应返回同一 taskId。用相同键修改请求内容，应返回冲突。重启工作者后检查未完成任务如何处理。

## 自测

### 1. 相同 requestId 携带不同请求内容，应怎样处理？

1. 随便复用旧结果
2. 拒绝冲突并说明原因
3. 再生成一个任务而不告知

<details>
<summary>答案与原因</summary>

答案：2。同一幂等键必须绑定同一业务意图。

</details>

### 2. 有了 outbox，就能无条件保证远程副作用恰好一次吗？

1. 能
2. 不能，派发重试仍要求接收端去重
3. 只要改为 Go 就能

<details>
<summary>答案与原因</summary>

答案：2。outbox 解决本地记录与待发送事件的一致性，不能消除所有跨系统重复执行窗口。

</details>
