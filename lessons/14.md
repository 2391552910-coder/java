# 14 · 并发与 JVM：限制负载，再定位瓶颈

第 11 周 · 首次讲解与小练习约 90 分钟，项目实践另计。

服务变慢时，先判断时间花在排队、计算、数据库还是模型。不要看到慢就加线程，看到内存高就盲目改 GC 参数。

## 有界并发

请求到达速度超过处理速度时会排队。无界队列推迟拒绝，却可能积累内存与不可接受的延迟。固定线程数、有限队列、明确拒绝策略与总超时共同构成容量边界。限流限制单位时间到达量，并发限制约束正在执行的数量；两者不同。虚拟线程降低部分阻塞线程成本，也不会让数据库和模型的容量无限增加。

## 共享数据与原子性

volatile 保证相关可见性与顺序约束，但 count++ 是读、计算、写的复合动作，仍可能丢失更新。AtomicInteger.incrementAndGet 可以完成原子递增；跨多个字段的业务不变量还需要更完整的同步或数据库事务。并发集合只保证其规定的单个操作语义，get 后再 put 不会自动组成原子业务。

## 诊断顺序

先记录吞吐、错误率、P95、队列长度与下游耗时。CPU 高时看热点；大量线程等待连接池时检查数据库和连接泄漏；内存持续上涨时区分缓存、任务积压和真正泄漏。用 jcmd 的线程信息或 JFR 捕获证据。堆是对象分配的重要区域，栈保存调用帧等；本课不靠一句“对象全在堆上”解释全部 JVM 优化。

## 联系你的 Python 经验

不要直接套用 Python GIL 的结论。Java 多线程可并行执行，但共享状态竞争和外部资源容量依旧要控制。

## 代码拆解

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 4, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(20),
    new ThreadPoolExecutor.AbortPolicy());
try {
    pool.execute(() -> performBoundedTask());
} catch (RejectedExecutionException ex) {
    // 映射为明确的过载响应，不能假装任务已受理。
}
```

需要 java.util.concurrent 包及 performBoundedTask 实现。4 与 20 是实验参数，不是生产推荐。应用关闭时需要 shutdown，并处理未完成任务；阻塞调用仍要有自己的超时。

## 自测

### 1. volatile int count; 的 count++ 是否原子？

2. 不是
3. 只要线程少于4个就是

<summary>答案与原因</summary>

答案：2。读取、计算和写入之间可能与其他线程交错。

### 2. 下游模型容量不变，持续增加线程一定提高吞吐吗？

1. 一定

<summary>答案与原因</summary>

答案：2。瓶颈容量没有随线程数自动增长。
