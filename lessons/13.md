# 13 · 流式响应与 Agent 工具：处理断连和副作用

第 10 周 · 首次讲解与小练习约 75 分钟，项目实践另计。

流式输出让用户更早看到进展，但不会自动缩短任务总耗时。工具调用也不是模型说执行就能不加限制地执行。

## SSE 的消息边界

SSE 使用 text/event-stream，事件以空行分隔，可带 event、id 与 data 字段。网络读取的一次 chunk 不等于一个完整事件，JSON 可能跨 chunk 分割；不能每收到一块字节就立即 JSON.parse。要缓冲到完整事件边界，再解析。原生 EventSource 通常使用 GET 且不能任意自定义 Authorization 头；鉴权方式要与客户端选择相匹配。

## 断连与背压

浏览器关闭后，Java 的连接应清理，下游是否取消按产品策略明确。若任务继续后台执行，保存 taskId 供用户重连查询；若取消，向工作者发送取消请求并等待确认。慢客户端可能堆积缓冲，需要上限与清理策略。不要为每个 token 新建线程或把所有输出无限存进内存。

## 工具参数不是可信指令

模型输出必须经 schema、类型、范围和权限校验。查询工具与写入工具分开，建单等副作用先展示计划并由用户确认；用户确认也不替代服务端权限。工具执行沿用幂等键，记录工具名称、时间和结果摘要，设置步数与成本上限。Agent 的说明文本不能作为“执行成功”的唯一证据。

## 联系你的 Python 经验

FastAPI 流式生成器与 Java 转发器都需要处理取消和资源释放。Python 的 yield 次数、Java 的读取块和浏览器收到的事件数量不一定一一对应。

## 代码拆解

```text
event: progress
id: 1
data: {"taskId":"t-1","stage":"retrieving"}

event: result
id: 2
data: {"taskId":"t-1","answer":"建议检查配置"}


```

两个事件各以空行结束。id 若用于断线恢复，还需要服务端保存并正确重放事件，单有编号并不自动实现恢复。
