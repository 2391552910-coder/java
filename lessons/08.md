# 08 · 事务与乐观锁：两次写入必须一起成功

第 7 周 · 首次讲解与小练习约 90 分钟，项目实践另计。

创建工单和写操作记录是一个业务动作。今天用故意制造的失败，检验事务真实生效，而不是只检查代码里有没有注解。

## 本地事务的边界

同一事务内的数据库操作可以共同提交或回滚。它不会撤回已经发出的邮件或已经成功的 HTTP 工具调用。长时间持有事务等待模型会占用数据库连接和锁，放大故障。先短事务保存任务，再由工作者执行外部操作，最后短事务记录结果，是后续可演进的方向。

## Spring 事务为什么可能不生效

常见代理模式依赖调用经过容器代理：同一对象内部 this 调用另一个带事务注解的方法不会额外经过代理。默认回滚规则通常覆盖 RuntimeException 和 Error，受检异常要按业务明确配置。异常若被吞掉并正常返回，事务可能提交。这里假定未额外修改全局回滚策略。

## 乐观锁防止悄悄覆盖

客户端读取 version=3，更新时执行 WHERE id=? AND version=3，同时把 version 加一。影响行数为 0 表示记录不存在或版本已变化，服务应区分并返回适当结果。version 不是自动魔法，必须真的出现在更新条件里。遇到冲突应重新读取并判断，不应无条件覆盖重试。

## 联系你的 Python 经验

与 Python 数据库事务类似，关键是连接与事务管理范围，而不是语言。@Transactional 可以类比声明一个执行边界，但必须有实际基础设施执行它。

## 代码拆解

```sql
UPDATE ticket
SET status = ?, version = version + 1
WHERE id = ? AND owner_id = ? AND version = ?;
-- 应用检查受影响行数：1 表示更新成功，0 表示未满足条件。
```

权限条件、ID 与版本一起参与更新，避免检查后被并发修改。Java Service 的事务应同时覆盖工单修改与事件写入。

## 动手任务

写一个通过 Spring Bean 调用的事务方法，先插入 ticket，再插入 ticket_event。第二步主动抛运行时异常；在方法结束后用独立查询确认两表均未留下本次数据。再模拟两个 version 相同的更新。

在本地 IDE 或终端实现并运行；网页不会编译 Java 或判定编程题正确。

## 自测

### 1. 同对象 this 调用带 @Transactional 的方法，默认代理模式一定开启新事务吗？

1. 一定
2. 不一定，该调用不经过代理
3. 只看方法名称

<details>
<summary>答案与原因</summary>

答案：2。自调用绕过代理；应检查实际调用边界与已有事务。

</details>

### 2. 事务回滚能自动撤销已成功的远程建单 HTTP 请求吗？

1. 能，只要在同一个 Java 方法里
2. 不能，本地数据库事务不控制远程副作用
3. 换 Redis 就能

<details>
<summary>答案与原因</summary>

答案：2。跨系统行为需要明确的幂等、状态协调或补偿策略。

</details>
