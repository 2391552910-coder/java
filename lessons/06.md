# 06 · HTTP、DTO 与参数校验：写清接口契约

第 5 周 · 首次讲解与小练习约 90 分钟，项目实践另计。

一个接口不只是返回 JSON，还要让调用者知道哪里成功、哪里失败、怎样修正。用 DTO 隔离外部输入和内部实体。

## 请求进入业务前发生什么

客户端发送方法、路径、请求头和请求体；框架把 JSON 转成 DTO，再执行校验并调用控制器。创建可以约定返回 201，参数非法返回 400，不存在返回 404，状态或版本冲突返回 409。状态码与响应体共同构成契约。DTO 不直接暴露数据库全部字段，可避免用户提交 ownerId、管理员标志等不该自行修改的数据。

## 校验分两层

@NotBlank 检查字段格式；“工单是否属于当前用户”“已关闭工单能否再关闭”是业务规则，不能只依赖 DTO 注解。引入 validation 依赖并在 @RequestBody 参数上使用 @Valid 才能触发相应校验。不要把任意 IllegalArgumentException 全部映射为用户错误，因为它也可能来自程序内部缺陷；使用明确的业务异常类型。

## 异常与演进

统一异常处理返回稳定的错误码、可理解的信息与 requestId；完整堆栈只记在服务端。添加分页上限避免无限读取，排序字段用白名单。下面片段演示控制器与 DTO，省略了实体、服务与 import，不是复制一个文件就能启动的完整工程。

## 联系你的 Python 经验

DTO 可类比 Pydantic 模型，但 Java 的 record、Jakarta Validation 与 Spring MVC 各负责不同工作；不是写了注解就自动把所有业务规则验证完。

## 代码拆解

```java
record CreateTicketRequest(@NotBlank @Size(max = 100) String title) {}
record TicketView(long id, String title, String status) {}

@RestController
@RequestMapping("/api/tickets")
class TicketController {
    private final TicketService service;
    TicketController(TicketService service) { this.service = service; }
    @PostMapping
    ResponseEntity<TicketView> create(
            @Valid @RequestBody CreateTicketRequest request) {
        TicketView created = service.create(request.title());
        return ResponseEntity.created(
            URI.create("/api/tickets/" + created.id())).body(created);
    }
}
```

@Size 的字符串长度不等于所有语言下的可见字数。本课先采用与第 1 课一致的 UTF-16 长度约定。实际鉴权与 ownerId 获取在第 9 课补充。

## 自测

### 1. @NotBlank 足以证明用户有权关闭工单吗？

1. 足够，校验通过就是可信请求
2. 不够，它只检查字符串格式
3. 只要用 record 就足够

<details>
<summary>答案与原因</summary>

答案：2。权限与业务状态必须在可信身份和数据上判断。

</details>

### 2. 重复关闭被约定为状态冲突，哪个响应更清楚？

1. 200 且 success=true
2. 409 并返回明确业务错误码
3. 只在服务端打印错误

<details>
<summary>答案与原因</summary>

答案：2。调用者需要能够区分成功与冲突，才能采取相应行为。

</details>

## 实践验收

- [ ] DTO 不开放敏感字段
