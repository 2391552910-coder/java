# 09 · 认证与授权：登录了，也不一定能访问

第 8 周 · 首次讲解与小练习约 75 分钟，项目实践另计。

最危险的一类业务错误是“请求合法、对象存在，但不属于这个用户”。先把资源归属验证做好，再优化界面体验。

## 身份和权限是两个问题

认证回答“你是谁”，授权回答“你能对哪个资源做什么”。前端传来的 userId 不可信。服务应从已验证的会话或令牌得到主体，再根据主体、资源和动作做判断。登录成功只能证明身份，不意味着可以读取所有知识库。

## 从入口到数据层

Spring Security 可以控制 URL 访问与认证流程，但 require authenticated 只要求登录，不能替代对象归属判断。查询使用 id 与 owner_id，或显式检查知识库成员关系。任务结果、下载链接、文档检索范围都要遵循同一权限规则，不能只保护管理页面。

## 选一种清晰的学习方案

第一版可以采用框架支持的会话登录：密码使用成熟 PasswordEncoder，浏览器请求携带会话；Cookie 应有适当属性，涉及 Cookie 身份的写操作保留 CSRF 防护。若采用 Bearer token，再单独理解过期、签名验证和撤销。CORS 只控制浏览器跨源读取行为，不是身份认证。不要为跑通请求一键关闭全部保护。

## 联系你的 Python 经验

FastAPI 的依赖函数和 Java 的安全上下文都可提供已验证身份；资源授权仍是业务责任。把 ownerId 放在请求体里不会让它自动可信。

## 代码拆解

```java
TicketView getForUser(long ticketId, long authenticatedUserId) {
    return repository.findByIdAndOwnerId(ticketId, authenticatedUserId)
        .map(TicketView::from)
        .orElseThrow(TicketNotFound::new);
}
```

这是业务片段。authenticatedUserId 由服务端认证流程提供。返回 404 可统一隐藏不存在与无权访问的差异；也可采用明确的 403 策略，但契约应一致。

## 自测

### 1. 接口要求登录，就能防止用户读取别人的工单吗？

1. 能
2. 不能，还需资源级授权
3. 只要 ID 难猜就能

<details>
<summary>答案与原因</summary>

答案：2。身份认证与对象授权不同，随机 ID 也不能替代授权。

</details>

### 2. CORS 是服务端身份认证机制吗？

1. 是
2. 不是，它主要约束浏览器跨源访问
3. 是，只要 Origin 写正确

<details>
<summary>答案与原因</summary>

答案：2。非浏览器客户端不受浏览器 CORS 规则约束；服务端仍必须认证和授权。

</details>
