# 10 · Redis 缓存：先定义失效和故障行为

第 8 周 · 首次讲解与小练习约 60 分钟，项目实践另计。

缓存是数据库之外的一份加速副本。今天明确缓存失效、数据更新和 Redis 故障时发生什么，避免把“接上 Redis”当作性能完成。

## 读路径与更新路径

常见 cache-aside：先读缓存，未命中查数据库，再写入带 TTL 的缓存。更新通常先提交数据库，再删除相关缓存。并发下仍可能发生旧读取回填，因此不能声称删除缓存实现了强一致；对不能容忍旧值的场景，考虑绕过缓存、版本校验或更强的协调机制。

## 键和值都需要契约

键含实体 ID 与必要的租户范围，序列化值有版本；TTL 控制旧值最长保留的一个因素，但还要考虑回填与延迟。不存在的对象可短暂缓存空结果，减少穿透，且不能把无权限和不存在随意混成全局缓存。关键权限第一版每次查可信来源，不把用户 A 的授权结果缓存给用户 B。

## 故障时有界降级

Redis 超时应快速失败；可回源数据库，但必须限流，避免所有流量压垮数据库。缓存击穿是热点失效后同时回源，可通过受控单飞、互斥加载等方式缓解；加入 TTL 抖动减少批量同时过期。先做观测，记录命中率、回源量与延迟，别盲目引入复杂锁。

## 联系你的 Python 经验

Redis 不是 Java 专属；你现有 Python 服务同样需要处理缓存一致性。这里练习的是数据副本与故障边界，而不只是客户端调用。

## 代码拆解

```text
读取元信息：
1. 验证用户对知识库的权限
2. 用 kb:meta:v1:{id} 查非敏感元信息缓存
3. 未命中则查数据库，写入有限 TTL
4. 返回 DTO

更新元信息：
1. 数据库事务提交
2. 删除对应缓存；失败时记录并安排重试
3. 对强一致读取不要依赖这个缓存
```

这是流程示意，不是 Redis 执行脚本。权限判定不依赖这个共享元信息缓存；重试失效需要持久化或明确的可靠处理方案。

1. 是
2. 否，可能发生旧查询回填
3. 只要 TTL 一小时就能

<details>
<summary>答案与原因</summary>

答案：2。并发操作的顺序可能让旧查询在删除之后写入旧值。

</details>

### 2. Redis 故障时所有请求无上限回源，主要风险是什么？

1. 数据库被流量压垮
2. Java 自动丢失类型
3. HTTP 变成 UDP

<details>
<summary>答案与原因</summary>

答案：1。降级也需要超时、并发限制和容量规划。

</details>
