# 04 · Maven、测试与调试：让错误稳定重现

第 3 周 · 首次讲解与小练习约 75 分钟，项目实践另计。

测试不是检查代码有没有执行，而是证明关键行为在成功、失败和边界输入下符合约定。先写你真正在意的业务结果。

## 构建流程

Maven 根据 pom.xml 管理依赖并执行构建生命周期。业务源码放 src/main/java，测试放 src/test/java。mvn test 运行测试，mvn package 还会打包；若项目提供 Maven Wrapper，Windows 使用 .\mvnw.cmd test。不要把“成功下载依赖”当作构建成功，检查退出码和测试摘要。

## 测试边界

对标题规范化至少覆盖 null、纯空白、100 和 101 个 ASCII 字符。对工单状态验证第二次 close 被拒绝。测试命名表达业务含义，Arrange 准备输入、Act 执行、Assert 检查结果。不要为了覆盖率把每个 getter 都测一遍，也不要把被测函数复制到测试里重新计算同一个错误答案。

## 从证据排错

读异常类型、第一处属于自己代码的堆栈和最内层 cause。设置断点观察进入方法前后的状态。日志放 requestId、任务 ID 和操作结果，避免输出密码、token 与完整私人文档。单元测试可替换外部服务，集成测试再验证真实 SQL 与事务，二者回答的问题不同。

## 联系你的 Python 经验

JUnit 的断言与 pytest 的 assert 用途相似；注解标记测试方法。可测试设计往往来自显式依赖，而不是引入尽可能多的 mock。

## 代码拆解

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class TitleTest {
    @Test void trimsOuterWhitespace() {
        assertEquals("故障", Titles.normalizeTitle("  故障  "));
    }
    @Test void rejectsBlankTitle() {
        assertThrows(IllegalArgumentException.class,
            () -> Titles.normalizeTitle("   "));
    }
}
```

这是测试片段，需要把第 1 课函数放进 Titles 类并配置 JUnit 依赖。下方 exercises/core 提供不依赖 Maven 的第一组可运行练习，先运行它建立反馈循环。

## 自测

### 1. 测试成功的合理含义是什么？

1. 程序不会有任何 bug
2. 被测场景符合当前断言
3. 外部模型效果一定很好

<details>
<summary>答案与原因</summary>

答案：2。测试的结论受输入、断言和环境限制。

</details>

### 2. 要验证真实 SQL 的事务回滚，仅使用内存 mock 是否足够？

1. 足够，方法名相同即可
2. 不够，需要真实事务环境的集成验证
3. 只需检查注解存在

<details>
<summary>答案与原因</summary>

答案：2。mock 不会实际执行数据库事务；注解存在也不能证明代理和事务配置生效。

</details>
